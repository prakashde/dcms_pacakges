1. What this project actually is

The workbench is a React application whose rules are authored and evaluated by two custom packages. The engine is built on Chevrotain (the parser toolkit, written “chevrotrain” in the brief) and Formula.js (the spreadsheet-function library, @formulajs/formulajs). The React package wraps the engine for the Workbench and for DCMS forms.

criteria labels, operators → dcmsFormAdapter.js
label ↔ enum conversion Workbench model
@dcms/form-rules-react → compileForm / evaluate
@dcms/form-rules → feedback, blockers,
canSubmit

2. Repository and branch model

One repository holds both packages. Each package has a long-lived customization branch, and every individual change gets a short feature branch. main is always the combination that is ready to release.

BranchPurposeRules
mainRelease-ready state of both packages.Only merge verified work. Tag releases from here.
custom/form-rulesLong-lived engine customization.Changes stay under packages/form-rules/.
custom/form-rules-reactLong-lived React adapter customization.Changes stay under packages/form-rules-react/.
feature/form-rules/<name>One engine change.Branch from custom/form-rules; merge back by PR.
feature/form-rules-react/<name>One adapter change.Branch from custom/form-rules-react; merge back by PR.
Because both packages share one branch history an engine version bump can be released without touching the React package. When the engine's public contract changes, update @dcms/form-rules-react's exact peerDependencies entry for @dcms/form-rules in the same release train.

Branch names used in this repository

main
custom/form-rules
custom/form-rules-react

git branch custom/form-rules-react
git push origin custom/form-rules custom/form-rules-react

Step 4

5. Build, test, pack, and publish a release

Consumers install built tarballs. Build and test before packing; the packing scripts refuse to run when dist/ or other required inputs are missing.

5.1 Prepare the version

  1. Change the version in the modified package's package.json (for example 0.10.6 or 0.4.0-parity.7).
  2. If the engine version changed, set the React package's exact peer to the new engine version.
  3. Update the package README version heading and add release notes.

5.2 Verify and pack

cd "D:\ALL PROJECTS\DCMS-form-packages"
npm ci
npm run build
npm test
npm run pack

# Inspect what will be uploaded
ls artifacts
tar -tzf artifacts/dcms-form-rules-0.10.6.tgz | grep -E "dist/|^package/node_modules/" | head

Expected artifacts (names follow the versions in the package manifests):

FilePurpose
dcms-form-rules-<version>.tgzEngine runtime: compiled ESM/CJS, types, docs, schemas, bundled runtime dependencies.
dcms-form-rules-react-<version>.tgzReact adapter: compiled ESM and .d.ts files.
*.tgz.sha256Checksum sidecar in <hash> <filename> format.

5.3 Commit, tag, push

Use one tag per package version. The examples below release the engine; repeat with the React names when only that package changed.

cd "D:\ALL PROJECTS\DCMS-form-packages"

git add packages/form-rules/package.json packages/form-rules-react/package.json
git commit -m "release(form-rules): 0.10.6"

git tag -a form-rules-v0.10.6 -m "form-rules 0.10.6"
git push origin main
git push origin form-rules-v0.10.6

5.4 Attach the artifacts to a GitHub Release

cd "D:\ALL PROJECTS\DCMS-form-packages"

gh release create form-rules-v0.10.6 \
  artifacts/dcms-form-rules-0.10.6.tgz \
  artifacts/dcms-form-rules-0.10.6.tgz.sha256 \
  --title "form-rules 0.10.6" \
  --notes "Describe the customization and any consumer-visible behavior."

For the React package, create a second release only when that package changed:

git tag -a form-rules-react-v0.4.0-parity.7 -m "form-rules-react 0.4.0-parity.7"
git push origin form-rules-react-v0.4.0-parity.7

gh release create form-rules-react-v0.4.0-parity.7 \
  artifacts/dcms-form-rules-react-0.4.0-parity.7.tgz \
  artifacts/dcms-form-rules-react-0.4.0-parity.7.tgz.sha256 \
  --title "form-rules-react 0.4.0-parity.7" \
  --notes "Describe the adapter change."
Tag and release names must match The DCMS download command uses the tag. A release asset is not a Git branch: consumers get the exact packed file you tested, not whatever is currently on main.

5.5 Optional: automate the release with GitHub Actions

Add .github/workflows/release.yml if you want GitHub to build and attach the tarballs on every package tag. The prompt in section 9 generates a reviewed workflow; do not add it until the manual release has succeeded once.

Step 5

6. Install the released packages into DCMS

DCMS consumes local tarballs from vendor/, updates the lockfile, and builds. This is the same mechanism the app already uses, so the change is small and reversible.

6.1 Download the release assets

cd "D:\ALL PROJECTS\DCMS"

gh release download form-rules-v0.10.6 ^
  --repo YOUR-GITHUB-USER/dcms-form-packages ^
  --pattern "dcms-form-rules-0.10.6.tgz*" ^
  --dir vendor

In Git Bash the line continuation is \; in cmd.exe it is ^. For the React package:

gh release download form-rules-react-v0.4.0-parity.7 \
  --repo YOUR-GITHUB-USER/dcms-form-packages \
  --pattern "dcms-form-rules-react-0.4.0-parity.7.tgz*" \
  --dir vendor

Without the GitHub CLI, open the release page and download the two files into D:\ALL PROJECTS\DCMS\vendor manually.

6.2 Verify the checksums

cd "D:\ALL PROJECTS\DCMS\vendor"
sha256sum -c dcms-form-rules-0.10.6.tgz.sha256
sha256sum -c dcms-form-rules-react-0.4.0-parity.7.tgz.sha256

On PowerShell:

Get-FileHash .\dcms-form-rules-0.10.6.tgz -Algorithm SHA256
Get-Content .\dcms-form-rules-0.10.6.tgz.sha256
A failed checksum means stop. Delete the downloaded file and download it again. Do not edit the sidecar or repack the tarball by hand; a mismatch means the upload or download is not the artifact that was tested.

6.3 Point DCMS at the new files

Install the tarball paths; npm updates both package.json and package-lock.json.

cd "D:\ALL PROJECTS\DCMS"

npm install "file:vendor/dcms-form-rules-0.10.6.tgz" --save-exact

# If the React package was also released:
npm install "file:vendor/dcms-form-rules-react-0.4.0-parity.7.tgz" --save-exact

If npm reports a peer-dependency conflict for React, first confirm the app still contains the existing override, then retry with the legacy resolver:

"overrides": {
  "@dcms/form-rules-react": {
    "react": "$react"
  }
}
npm install "file:vendor/dcms-form-rules-react-0.4.0-parity.7.tgz" --save-exact --legacy-peer-deps

Prefer the override. --legacy-peer-deps is a fallback; it can hide a real React 18/19 incompatibility.

6.4 Confirm resolution and build

cd "D:\ALL PROJECTS\DCMS"
npm ls @dcms/form-rules @dcms/form-rules-react
npm run build:clientdev

Expected: both packages resolve to the new versions, the React package is marked overridden for its React peer, and the CRA production build completes.

6.5 Run the adapter tests

cd "D:\ALL PROJECTS\DCMS"
CI=true npm test -- --watchAll=false src/common/FormBuilder
These tests do not exercise the package's ESM entry point. CRA's Jest 27 cannot resolve the React package's exports map, so the adapter tests virtual-mock @dcms/form-rules-react. Real integration is proven by the CRA build plus loading the form pages in a browser. The engine package itself is exercised by the 164 Node tests in the package repository.

6.6 Commit the consumer change

cd "D:\ALL PROJECTS\DCMS"
git add vendor package.json package-lock.json
git commit -m "chore(deps): update DCMS form packages from release"
git push

Committing vendor/ is intentional in this app: teammates and CI get the exact tested bytes without cloning or building the package repository.

6.7 Roll back

cd "D:\ALL PROJECTS\DCMS"
git revert HEAD --no-edit
npm ci
npm run build:clientdev

Or restore the previous tarball paths in package.json, run npm install, and rebuild. Keep the old release assets on GitHub; do not overwrite a release asset in place.

Checklist

7. Verification checklist

In the package repository

  • npm ci completes from a clean checkout.
  • npm run build succeeds for both workspaces.
  • npm test passes all engine tests (164 at this baseline).
  • npm run pack creates both tarballs and matching .sha256 files.
  • tar -tzf shows package/dist/... and, for the engine, package/node_modules/chevrotain.
  • The released tag points at the commit you built.
  • The GitHub Release contains the same checksum sidecars as artifacts/.

In DCMS

  • sha256sum -c passes for every downloaded asset.
  • package.json uses the new file:vendor/... path.
  • npm ls @dcms/form-rules @dcms/form-rules-react shows the expected versions and no invalid peer warning.
  • The React override is still present.
  • npm run build:clientdev succeeds.
  • The Form Builder page loads, a form with validation rows evaluates, and Submit is enabled/disabled as expected.
  • vendor/, package.json and package-lock.json are committed together.

When it fails

8. Troubleshooting

SymptomCauseFix
ERESOLVE unable to resolve dependency tree mentioning react@19.3.0 The React package's peer is React 19; DCMS runs React 18. Keep overrides["@dcms/form-rules-react"].react = "$react". Retry with --legacy-peer-deps only if the override is present and npm still refuses.
Cannot find module '@dcms/form-rules' Install not run at the DCMS root, or the file: path is wrong. Run npm install from D:\ALL PROJECTS\DCMS; check that the filename in package.json exists exactly in vendor/.
Jest: Cannot use import statement outside a module or an exports map error CRA's Jest 27 does not transform the ESM-only adapter package. Keep the existing virtual mock in adapter tests. Verify the real package with react-scripts build and the running form pages, not by importing it directly into Jest.
Missing package input … Run npm run verify before packing dist/ or another required input was not built. Run npm run build (or npm run pack, which builds first) before packing.
Runtime closure needs multiple lodash installations The workspace resolved two Lodash versions, so the engine packer cannot flatten the runtime tree. Confirm the root package.json has "overrides": { "lodash": "4.18.1" }, then delete node_modules and package-lock.json, run npm install, and pack again.
spawnSync npm ENOENT or EINVAL Node cannot spawn the npm shell shim on Windows. Run the pack through npm run pack; the included tools invoke npm through process.execPath + npm_execpath.
git push rejected (non-fast-forward) Someone pushed to the branch first. git pull --rebase, rerun the build/tests, then push. Never force-push main.
GitHub says “Protected branch update failed” main requires a PR. Push the feature branch, open a PR, and merge through GitHub.
Checksum mismatch in DCMS Partial download, wrong asset, or edited tarball. Re-download from the release; compare with the asset's published .sha256. Do not regenerate a sidecar to match a modified file.
Form behaves differently after an update The new engine semantics were not exercised against the DCMS field/row shapes. Revert the vendor files, then add a regression test at the adapter boundary and rerun the package's engine tests.
Git reports thousands of node_modules files You are inside the old distribution workspace, not the clean repository. Use D:\ALL PROJECTS\DCMS-form-packages; its .gitignore excludes dependencies, builds and artifacts.

Why tarballs instead of a direct git+https dependency? npm does not support installing a package from a subdirectory of a Git repository. This repo is a monorepo (packages/form-rules, packages/form-rules-react), so npm install git+https://github.com/… would try to install the repository root. Release tarballs are the reliable npm path and preserve the exact tested build. If you later need direct Git installs, split each package into its own repository or use a private npm registry; do not point DCMS at a branch and hope it builds.
Keep the source and the artifact in sync The Git tag identifies the source commit; the release asset identifies the built bytes. Record the tag in DCMS commit messages (for example form-rules-v0.10.6) so a production build can be traced back to both.
